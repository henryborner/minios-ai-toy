# MiniOS 内存扩容执行表

审查日期为 2026-11-26，目标分支为 `v2-protected-c`。基线为本地与 GitHub 均已确认的 `0f7c37a73fd1af921082de094992f2021acfc936`。本文件的代码位置按该提交标注。后续提交若已修复某项，用该项的回归用例验证，通过后从下一项接手。[本次提交](https://github.com/henryborner/minios-ai-toy/commit/0f7c37a73fd1af921082de094992f2021acfc936)

**给 DS 的首项任务是修复单页分配提前耗尽。** 在 32 MiB 客机上，启动早期有 6,112 个可用页框。用现有分配器每次申请一页，第 192 次就返回失败，当时还有 5,921 页空闲。这个问题会影响页表、进程堆和 RAM 文件，增加 QEMU 内存或延长等待时间都无法使被跳过的页进入本轮搜索。

## 怎样算完成

| 交付点 | 使用者能做什么 | 验收边界 |
| --- | --- | --- |
| A · 现有页框池可信 | 在已管理的 RAM 中逐页分配、写入、用尽、释放、再分配 | 64 页固定样例交付 64 页。客机受控池也能用尽。固件保留页始终排除，计数与实际分配一致 |
| B · 物理内存随机器增长 | 给同一镜像配置 768 MiB、1 GiB、2 GiB，新增的可寻址 RAM 进入分配器，进程能够实际使用高页框 | 跨过当前 512 MiB 物理上限，串口记录实际物理页地址、数据校验及回收。保留区、页表和内核元数据逐项入账 |
| C · 程序可用的内存随需求增长 | 一个普通 Ring 3 进程跨多个页表增长、收缩、退出。一个 MicroPython 进程能保留远超原有 1.5 MiB 的活对象 | 建议用 128 MiB 客机验收 16 MiB 原生进程堆和 8 MiB Python 活对象，用 256 MiB 客机验收 64 MiB 原生进程堆；均以实际写读、进程退出和页框回收为准 |
| D · 超出 32 位基础版 | 若目标是整机用上 4 GiB 以上物理内存，走 PAE。若目标是单个原生进程拥有超过 4 GiB 的虚拟空间，走 x86-64。若目标是工作集超过 RAM，另做磁盘换页 | 分别交付物理地址、进程虚拟地址、换入换出的证据。按需要选择，可独立排期 |

本计划把“真无限”定义为**消除项目写死的容量上限，让容量由机器可用 RAM、分页模式、进程虚拟地址空间和可选后备存储决定**。现有 i386 普通 4 KiB 非 PAE 页表能表示 4 GiB 以下的物理页，单个 32 位进程的整个线性地址空间也只有 4 GiB，其中还需给内核和保留映射留位置。PAE 扩展整机可用物理地址；64 位原生进程才能越过 32 位进程地址边界。两条路线均有 CPU 实现上限。[Intel 系统编程手册，第 3A 卷第 4 章](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html)

## 基线实测

使用 QEMU 11.0.1，从 Git 对象取出提交中的 `MiniOS-C.img`，用只读软盘逐档冷启动。镜像为 1,474,560 字节，SHA-256 为 `58edb7f725ce26dce265dd1d2f93d5ce5931d9831c1d132d53e21a17ce8c4843`。每页 4,096 字节。通过 HMP 从客机物理内存读出 BIOS 交接表，再与客机串口的 `metrics` 对照。

| 客机 RAM | 启动后空闲页 | 内核管理页 | E820 在 512 MiB 及以上报告的可用页 | 客机 selftest |
| --- | ---: | ---: | ---: | --- |
| 32 MiB | 5,996 | 6,112 | 0 | PASS |
| 64 MiB | 14,188 | 14,304 | 0 | PASS |
| 128 MiB | 30,572 | 30,688 | 0 | PASS |
| 256 MiB | 63,340 | 63,456 | 0 | PASS |
| 512 MiB | 128,876 | 128,992 | 0 | PASS |
| 768 MiB | 128,908 | 129,024 | 65,504 | PASS |

六档的管理页数都等于这台虚拟机 E820 在物理区间 `[8 MiB, 512 MiB)` 中报告的可用整页数。768 MiB 档另有 255.875 MiB 可用 RAM 位于上限之外。从 512 增到 768 MiB，内核总数仅多 32 页。128 MiB 档另跑了 `regress`，收到了预期的 `SYNC_FAIL`（只读盘）、`APPEND 0AB`、`SEEKEND 3` 和 `STATUSES 5 5`。当前 `selftest` 主要开关和绘制 Canvas，覆盖的是启动和 GUI 路径。[现有内存记录](memory-e820.md) · [GUI 自检](../c/gui.c) · [现有冒烟脚本](../tools/smoke_test.py)

为确认空闲数能否兑现为实际可用页，在宿主和客机分别运行了分配测试。

| 环境 | 做法 | 实际结果 |
| --- | --- | --- |
| 宿主 C 测试 | 编译该提交中原样提取的 `frame_mark_range`、`frame_alloc_pages` 和 `kernel_free_frames`，提供已映射的测试页表。将物理 8 MiB 起连续 64 页置为空闲，其他位置为已用，连续申请单页 | 仅 2 次成功，随后返回 0，计数仍显示 62 页空闲 |
| 宿主 C 测试 | 在同一空池中分别登记 48 页和 32 页，两段重叠 16 页 | 唯一可用页 64，`frame_total` 却为 80 |
| 32 MiB QEMU 诊断副本 | 先重链原内核，确认其 88,920 字节与提交镜像内核逐字节相同。再只在 `task_system_init()` 后加探针，使用原分配和释放函数。保留全部已分配页，写入与物理页地址相关的三组标记，第二遍校验后统一释放 | 初始 6,112 页，仅分到 191 页就返回 0，当时还剩 5,921 页。127 个物理地址至少为 16 MiB 的页校验成功，最高页地址 `0x01FC0000`，数据差错 0。释放后回到 6,112 页，客机继续启动并通过 `selftest` |
| 同一诊断副本，对照试验 | 只将命中占用位时的 `start = (bit / 32) * 32 + 31` 换为 `start = bit`，由外层循环执行下一次 `start++`。同一台 32 MiB 客机、同一探针再跑一次 | 初始 6,112 页，成功 6,112 次，下一次返回 0 时空闲为 0。4,064 个物理地址至少为 16 MiB 的页校验通过，全部页的数据差错为 0，释放回到 6,112，随后 `selftest` 通过。这处修改仅用于临时实验 |

第三项是启动早期、分页已打开的内核分配测试；上表第一列的 5,996 是正常桌面启动后的空闲数。两次取样时机不同。实测证明了当前直接映射上确有高于 16 MiB 的页能写读。512 MiB 以上的页、跨页表用户堆和换页属于下文的待验收项。
